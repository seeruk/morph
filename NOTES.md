# Notes

## How can Morph avoid using functions that it will generate code for?

Morph files are generated with a specific file header, and we pick up on this in the type loader. We
only worry about this for functions, not methods, since Morph only generates functions, hence the 
loader only marks whether a function has been generated by Morph.

It is expected that if you run Morph multiple times (i.e. for libraries separately to apps, etc.) 
then you'd still only ever run Morph once for each output group. This is a prerequisite assumption
that must be made for solving this problem.

Nested mappers in generated code, which are not explicitly referenced in the spec, could be 
generated as unexported functions. This would immediately make them unavailable for discovery. This
would then mean that when we're determining whether a function can be used by auto-discovery, only 
explicitly requested mapping functions could ever be used, including across multiple Morph runs. 
Therefore, if a mapping function was not explicitly requested _in this run_, it can safely be used.

So, upfront in the planning process, we should keep track of all the explicitly requested functions 
that will be planned, and then while actually planning them, we can safely handle auto-discovery.

The only potential flaw in that plan is that if multiple Morph runs can generate code into the same
package, the unexported functions from one run would be in the same package and could collide. This
could be avoided pretty easily by doing something like generating a spec-based unique prefix or 
suffix for all nested functions. They'd still never be used for discovery, so the only concern is
this potential naming collision.
